# VFL animation audit

**2 November 2026 · Scope: vfl only · Analysis and captures; gameplay code unchanged**

## Assessment

The fast, jittery feel has concrete causes. Some effects explicitly jump between positions, several large movements use a sharply front-loaded easing curve, and animation systems sometimes compete for the same element. Fixing the choreography is a better starting point than increasing every duration.

The isolated desktop solo recording had a median animation-frame interval of **16.7 ms**, a 95th percentile of **16.7 ms**, and **5 intervals over 33.4 ms in 5,572 samples**. This is consistent with a mostly steady 60 Hz callback cadence on this machine. It does **not** measure compositor presentation, establish an app-wide FPS guarantee, or represent slower phones. Much of the sample includes idle time. Video encoding, screenshots, and instrumentation also affect results.

## Findings, ordered by impact

### 1. Pack emergence and the stage jolt both own the same transform — high priority

**Confirmed in a controlled runtime capture.** `PackRip.jsx` animates `stripCards` using Anime.js: translation and scale over **480 ms**. `PackRip.module.css` applies `packStageJolt` to that **same element** whenever it contains a high-tier impact card. That animation starts after **360 ms** and lasts **120 ms**, overriding the inline transform during the last part of emergence.

Recorded example: the inline style was `translate(0px, 0px) scale(0.9954)` while the computed style was `matrix(1, 0, 0, 1, 0, 0)`. Subsequent samples jumped horizontally to −1.5, −3, +3 and +1.5 px. See `fixture-runtime.json`, `audit.samples`. The scale difference is small near the end; the horizontal jumps are intentional but mechanically discontinuous. For other entrance offsets, overriding the translation also risks a larger discontinuity.

The card itself has a second `rarityJolt`, plus an edge flash. This stacks whole-row movement, card movement, card springs and light punctuation in one beat.

**Recommendation:** give the emergence transform one owner. Move rarity punctuation onto a nested material layer, and prefer a restrained edge/opacity cue. If movement remains, apply one smooth impulse after the group has settled. Do not simply slow the stepped jolt.

Sources: `src/components/PackRip.jsx:87`, `src/components/PackRip.module.css:108`, `:124`; `shared/src/styles/tokens.css:143`.

### 2. Match events can interrupt their own animations — high priority

**Confirmed from scheduling and animation definitions; not every specialty combination was triggered.** A specialty is replaced every **140 ms** at Normal speed, but its chip and player pulse each run **200 ms**. The pulse travels **10 px upward in its first 32%**. Each subsequent trigger can remove the previous chip before completion. The score threshold adds an **80 ms stepped horizontal shake**.

A committed score has a **240 ms minimum hold**, while its keyed number entrance lasts **320 ms** at Normal speed. With no specialty gap, the next round remounts the number before the animation settles. At Fast speed, specialty gaps become **63 ms** while CSS specialty durations remain **200 ms**. Different animation layers therefore accelerate by different amounts.

**Recommendation:** start with **250–350 ms** per highlighted specialty and **400–550 ms** per ordinary score beat; hold important rounds longer. These are proposed design values, not measured requirements. Group simultaneous specialties into one legible highlight. Keep the score stable and animate a separate winner accent; remove the repeated positional reset and threshold shake. Advance from animation completion plus a readable hold rather than unrelated timers.

Sources: `src/pages/PerfectRun.jsx` (`ROUND_SCORE_HOLD_MS`, `revealRound`, keyed `castBig`), `src/pages/PerfectRun.module.css:1540–1578`.

### 3. Solo bracket travel applies Fast speed twice — high priority

**Confirmed by code calculation; full Fast-mode gameplay was not recorded.** The caller scales `TRAVEL_MS = 600` by run speed. `flyBracketMoves()` then sets Anime's playback speed using the inverse of the same multiplier. Fast uses 0.45, producing **600 × 0.45 × 0.45 = 121.5 ms** travel instead of the expected **270 ms**. The normal-duration path is unaffected. Multiplayer supplies the unscaled base duration, so its call does not have this same double scaling.

**Recommendation:** pass base durations into the flight helper and scale once inside it. Treat readable pauses separately from motion duration. The stored speed preference is read without an exposed setter in the current solo page, so existing browser preferences can also explain different pacing between profiles.

Sources: `src/pages/PerfectRun.jsx` (`travelDuration`), `src/lib/bracketFlight.js:55–65`, `shared/src/lib/anime.js:31–36`, `shared/src/lib/useRunSpeed.js:12`.

### 4. Library inspection uses a whole-page transition instead of a matched card morph — medium/high priority

**Confirmed in desktop runtime events and source.** Collection assigns `view-transition-name: focused-card` to the grid/list source. There is no corresponding name on the destination overlay card. No custom view-transition styling is authored. Browser events show the default **root fade-in/fade-out** on inspection and closing.

The overlay also plays its own **320 ms fade in / 150 ms fade out**. The combined result is a page crossfade plus overlay fade, rather than the intended card travelling between matching positions.

**Recommendation:** pair a unique transition name on the actual destination and source, and suppress the root crossfade for that transition, or use one existing shared-layout mechanism consistently. Verify open, close, rapid reopen and filtered/list sources separately.

Sources: `src/pages/Collection.jsx:43–60`, `src/components/CardFocusOverlay.jsx:109–112`; library runtime animation events beginning `-ua-view-transition-`.

### 5. The house easing front-loads large movement — medium priority

**Confirmed design setting.** The common curve is `cubic-bezier(0.2, 0.8, 0.2, 1)`. Numerically, it covers approximately **77% of displacement in the first quarter of elapsed time** and **95% by halfway**. A map travels **80 px in 320 ms**, so most of that move happens very early. Tactic hands travel 50 px on the same timing. A long tail does not make the initial movement feel slow.

**Recommendation:** keep quick feedback on buttons, but give large deals a more balanced ease, **450–550 ms**, and less travel (roughly 24–40 px). Tune distance and curve together. The current **120–150 ms** colour feedback is reasonable and does not need global slowing.

Sources: `shared/src/lib/motion.js:8–27`, `src/components/SeriesCardTable.jsx:297`, `:461`.

### 6. Phase exit sequencing is not keyed at AnimatePresence's direct child — medium priority

**Source-confirmed structural issue; needs a dedicated transition reproduction after fixing.** The parent renders conditional `PhaseTransition` components under `AnimatePresence mode="wait"`, but passes `phaseKey` only as a prop. The explicit key is on the nested `m.div`. The direct children seen by AnimatePresence have no explicit scene key, undermining reliable detection and sequencing of scene exits.

**Recommendation:** put the stable scene key on each direct `PhaseTransition` child, or render one keyed direct child. Then verify that exit and entry run once and that a child CSS entrance does not duplicate the parent movement. Do not assume that a prop named `phaseKey` is a React key.

Sources: `src/components/PhaseTransition.jsx:13–16`, `src/pages/PerfectRun.jsx` (`AnimatePresence mode="wait"` and scene wrappers).

### 7. Card motion has several simultaneous layers — medium priority

**Observed components; causal contribution varies by interaction.** PlayerCard has spring tilt, elevation, velocity-derived roll, direct pointer parallax, 150 ms child-plane transitions, drag elasticity and press scaling. Pack cards can add fan angle, row lean and breathing. Dock hover adds its own lift and neighbour movement. Different elements own many of these transforms correctly; their combined movement can still feel busy.

The tilt allows **±12° pitch/yaw and ±12° roll**; hover lifts 16 source px and press lifts 28 source px, before display scaling. In pointer movement, glare and layer position change directly while the outer tilt follows a spring.

**Recommendation:** first try ±5–7° tilt, much smaller or no velocity roll, one visible elevation response, and calmer glare. Retain spring continuity. Compare one card at a time before adjusting spring constants. Avoid attributing all motion to dropped frames.

Sources: `shared/src/lib/useCardTilt.js`, `shared/src/components/PlayerCard.jsx:101–120`, `shared/src/components/PlayerCard.module.css:219–225`, `src/components/SquadDock.module.css:58–89`.

### 8. Scroll lean is refresh-rate dependent — medium priority

**Confirmed in the equation.** `useScrollLean` derives its target from scroll-event delta and multiplies it by **0.9 per frame**. The target's half-life is about **110 ms at 60 Hz** and **55 ms at 120 Hz**. Event-frequency changes also change the input delta. The spring integration uses elapsed time, but the input decay does not.

**Recommendation:** derive lean from scroll velocity in pixels/second and use elapsed-time exponential decay. Reduce the 14° maximum. Verify trackpad, wheel, touch and both 60/120 Hz. Frame clamping in the spring loops also merits a slow-frame test; no instability was proved here.

Source: `src/lib/useScrollLean.js:5–7`, `:38–49`, `:69–72`.

### 9. Backdrop punctuation is extremely short — medium priority

**Captured component and source-confirmed durations.** Mild shakes fit five horizontal segments into **80 ms**; the strong shake uses **200 ms**, and the vignette fades in **150 ms**. At 60 Hz, an 80 ms shake spans roughly five frames total. The backdrop also changes image on tension escalation, with a **700 ms image fade** and **800 ms zoom** to 1.14 or 1.25.

**Recommendation:** remove routine micro-shake, reserve one gentler 250–350 ms reaction for decisive events, and keep the image stable through escalation. Evaluate zoom and image change separately. Current comments describing a 480 ms shake are stale: the executable values are 80/200 ms.

Source: `src/components/MatchBackdrop.jsx:18–33`, `:64–71`, `src/components/MatchBackdrop.module.css:30`.

### 10. Countdown rendering can do unnecessary work — lower priority, profile before changing

**Source-confirmed mechanism; not established as a dropped-frame cause.** `useSkippableTimeline` sets React state every animation frame. Several instances live in the large solo page. Its fill also has a **120 ms CSS transition**, continuously retargeted by those updates. Multiplayer timer samples arrive every 100 ms and are smoothed by a 120 ms transition.

**Recommendation:** drive the continuous fill through a motion value or one elapsed-time transform animation; update displayed seconds only when they change. Keep countdown completion exact. Investigate component render costs with a trace before claiming a performance bottleneck.

Sources: `src/lib/useSkippableTimeline.js:65–72`, `src/pages/PerfectRun.module.css:164`, `src/pages/Multiplayer.jsx` timer intervals, `src/pages/Multiplayer.module.css:68`.

## Proposed tuning pass

1. **Correct ownership and timing bugs first:** isolate pack transforms; scale bracket travel once; key phase children correctly; repair inspection pairing.
2. **Remove high-frequency positional noise:** whole-stage jolts, threshold shake, routine 80 ms backdrop shake, repeated score y-reset.
3. **Tune large movement independently:** map/tactic deals 450–550 ms with smaller travel and balanced ease; keep button feedback 120–150 ms.
4. **Make information readable:** specialty chips 250–350 ms minimum; ordinary score holds 400–550 ms; longer decisive-round holds. Provide explicit skip/fast controls if preserving speed preferences.
5. **Calm physical cards:** reduce tilt and velocity roll, align parallax response, make scroll decay time-based.
6. **Then profile actual bottlenecks:** low-end phone + Safari, 60/120 Hz, reduced motion, and recordings without instrumentation. Do not spend the first pass on global GPU hints or blanket duration increases.

## Acceptance checks for a follow-up fix

- No element has two systems writing its transform during the same beat.
- A 600 ms flight in Fast mode measures about 270 ms, not 121.5 ms.
- Specialty chip lifetime is at least its entrance/exit sequence plus readable hold.
- Ordinary scores settle before the next number is introduced.
- Opening/closing a library card does not fade the whole library unintentionally.
- A scene plays one exit followed by one entrance, including rapid navigation.
- Scroll lean has comparable decay time at 60 and 120 Hz.
- Reduced motion removes spatial motion in both flip directions and all imperative helpers; reading time remains sufficient. Existing CSS and MotionConfig support is a good base, but broad compliance was not established by one library recording.
- Capture multiplayer host/guest and real season transitions before claiming complete runtime coverage.
